# Project context

**AtmosHear** — Weather you can hear and feel.

Always write the name as "AtmosHear" (capital A, capital H). The slug, scheme, and package name stay `immersive-weather` / `immersiveweather` so the Expo project link doesn't break.

Multi-sensory weather app for a DES 156 class project, due 10/29/2026. This is the author's first mobile app: build in small steps and briefly explain each one.

## Concept

Each weather condition has its own sound, vibration pattern, and color so users can understand the forecast without looking at the screen. Accessibility for vision-impaired users is the core goal. A teammate is sourcing sounds and another is finalizing visual style, so keep sounds and colors easy to swap.

## Stack

- Expo SDK 58 (React Native 0.88) + TypeScript + Expo Router (routes in `src/app`). Expo Go only runs the latest SDK, so upgrade when it updates.
- Weather: Open-Meteo first, then the NWS API as backup, then the last saved forecast, then demo data (`src/services/weather.ts`). Every provider in `src/services/providers/` returns the shared `WeatherData` type (`src/services/weather-data.ts`); the rest of the app only uses that type. NWS requests must send a User-Agent header. Air quality (US AQI) is a separate Open-Meteo Air Quality request made alongside whichever provider answers (`src/services/air-quality.ts`, levels in `src/constants/air-quality.ts`); `WeatherData.airQuality` is null when it fails, and the last good value is saved separately for offline use. Severe alerts from the NWS API later.
- Vibration uses `expo-haptics` (works in Expo Go). Some patterns move to Core Haptics (AHAP) later in a dev build; until then, everything must run in Expo Go.

## Conditions

clear, partly cloudy, overcast, light rain, heavy rain, thunderstorm, snow, sleet, hail, fog, wind, extreme heat, extreme cold, severe alert (14).

Conditions can overlap (e.g. rain + wind). The most significant one (`src/constants/condition-priority.ts`) shows its icon and is named first: severe alert, then hail, then thunderstorm, so thunderstorm + hail shows the hail icon and reads "Hail and thunderstorm". Hail comes from Open-Meteo's thunderstorm-with-hail codes (96 and 99, as thunderstorm + hail; 95 is thunderstorm only) or NWS text that mentions hail. A single condition profile file maps each condition to its sound file, haptic pattern, color, icon, and light animation.

## Condition sounds

To add or replace a sound file, use the `add-condition-sound` skill (`.claude/skills/add-condition-sound/SKILL.md`): file naming (a replacement may use a `new-` prefix, e.g. `new-sleet.m4a`, so the old file stays for comparison), the one-line profile change, and the per-file loudness table (several files are intentionally softer or louder and must not be normalized). Every condition sound except overcast and thunderstorm is a `new-` file: 10-second loops exported at their targets (clear, extreme heat, fog, sleet, and hail -27.3 LUFS; partly cloudy and extreme cold -28.0; heavy rain -24.3; light rain -33.5; snow -28.3; wind -30.4), so none uses `soundVolume`. Extreme cold's loud ice cracks come about every 1.17 s, starting at 1.34 s, and its haptic triplets land on the first three.

Playback (looping, crossfades, layering overlapping conditions, background pause, VoiceOver ducking, the Preferences toggle and the home screen mute button, which share one `ambientSound` setting) is handled by `src/services/ambient-sound.ts` for every condition; nothing else needs to change. When conditions overlap, every one with a sound plays as its own layer, each at `1/√layers` volume (about 71% for two) so the mix isn't louder than one sound; conditions without a file are skipped. Each profile with a sound also stores its measured integrated loudness as `lufs` (the levels above, plus overcast -29.1 and thunderstorm -21.2), used to balance the weather under an alarm tone; a development check warns about a sound without one. Background sounds set `supportingVolume` in their profile to sit under other sounds (overcast and partly cloudy: 60%; wind: 50%, or 30% under snow and 25% under light rain via `supportingVolumeWith`) and play at full level when they're the only sound. `supportingVolumeWith` also works on its own: thunderstorm stays a main sound but drops to 50% under hail, so the hailstones aren't buried.

## Vibration

Each condition's `haptic` field in `src/constants/condition-profiles.ts` is a pattern of timed taps (`{ at, style }`, helpers in `src/constants/haptics.ts`); patterns differ mainly by rhythm. `src/services/haptics.ts` plays them (one sequence at a time, never looped; on web the timers run, and tap listeners fire, but nothing vibrates), and `src/hooks/use-condition-haptics.ts` decides when: once when weather loads, when the conditions change, and when the weather icon is tapped. Combinations play the most significant pattern, then the next after 400 ms. The Preferences "Vibration" toggle turns condition patterns off; the severe alert pattern plays with each alert beep regardless, and a condition pattern can't interrupt it.

## Severe alert sound

Alerts are separate from the ambient condition sounds. `assets/sounds/severe-alert.m4a` (a beep plus a short pause, set in `src/constants/alert-sound.ts` with the repeat count and duck level) plays 3 times back to back at full volume when a new alert appears or the app opens with one, while the ambient sounds duck to 20%. Then the conditions underneath keep playing; `severe-alert` itself has no ambient loop. It ignores the "Ambient sound" toggle and VoiceOver ducking, beeps once per alert ID per session, and announces "Severe weather alert: <name>" after the beeps. Tapping the weather icon during an alert replays it. Logic: `src/services/alert-sound.ts` and `src/hooks/use-alert-sound.ts`. Alerts come in as `WeatherData.alert` (`{ id, name }`); only test weather sets it until NWS alert fetching is built. When it is, the alert ID must stay stable across refreshes, and think about whether a saved (cached) forecast should keep its alert.

## Cue screens

Two root-stack screens show and preview each condition's cues. The Sound library (`src/app/sounds.tsx`, a "Sounds" title, then rows with a play button) opens from the All sounds square button at the top of the Weather screen, which passes the current conditions as `current`: they come first under "Right now" (most significant first), then all 14 under "All conditions". Opened without current weather, it leaves out "Right now" and shows just the list. Tapping a row opens condition detail (`src/app/condition/[id].tsx`, the condition PNG inside pulsing `DotRings`, see Design direction); its back button returns to the library. There is no Feel & hear screen any more (frame 08 is unused). The copy comes from each profile's `soundDescription`, `vibrationDescription`, `vibrationDetail`, and `lightDescription`, which must describe what actually plays: update them when a sound file or haptic pattern changes. Each profile's `contrastPair` names two `cueColors` (`src/constants/theme.ts`); the ratio is computed by `contrastRatio` (`src/constants/contrast.ts`), never typed in. A development check logs any pair under 4.5:1 or any light cue over the flash limit.

- Light cues (`light` in each profile, helpers in `src/constants/light-cues.ts`) play as a full-screen color overlay (`src/components/light-overlay.tsx`, mounted in the root layout) that never takes taps or VoiceOver focus. Never more than 3 flashes per second (WCAG 2.3.1): `safeLightCue` swaps an unsafe cue, or any cue when Reduce Motion is on, for a gentle fade.
- Previews (`src/services/cue-preview.ts`, `useCuePreview`) play sound, vibration, and light together, one condition at a time, for at least 8 seconds. Sound goes through `ambientSound.setPreview`, which pauses the Weather loop and crossfades back after; previews play even with "Ambient sound" off. Vibration follows the Vibration setting (the rows say when it's off), also for the severe alert preview, whose beeps come from `alertSound`. Previews stop when their screen closes or the app goes to the background.

## Must-haves

- Live weather by location with a Bethlehem, PA fallback.
- Demo mode to force any condition.
- Sound-only / vibration-only / light-only modes.
- High-contrast theme.
- °F / °C setting (Preferences › Temperature: Auto, °F, °C). Auto (default) uses the usual unit in the country of the last live location (`src/constants/temperature-units.ts`, country saved as `locationCountry`), or the phone region's before the first one. Weather data stays in °F; components convert for display with `useTemperature()`.

## Developer mode

Preferences › Developer replaces live weather with filler data for testing and presenting (no API calls), or forces one live provider (Open-Meteo or NWS, no fallback). All filler values and the list of test conditions and combinations live in `src/constants/test-weather.ts`; `src/services/providers/demo.ts` turns them into a 12-hour forecast. The same filler is the last-resort fallback when no live or saved weather exists. A "Developer mode" pill always shows on the home screen while it's on. The "Severe alert" test weather comes with a test alert over thunderstorm + heavy rain, beeping each time it's picked; "Replay alert" in the Developer section plays the beeps on demand. "Replay onboarding" (also while Developer mode is on) clears `onboarding.completed` and opens `/onboarding/welcome`.

### How alarms ring

- **Tones:** `alarm-tones.ts` maps each `tone` (`morning` default, `digital`, `generic` shown as "Classic", `dreamcore`) to its file in `assets/sounds/alarms/` (names kept as delivered; don't rename). The editor's Sound row opens the tone list with one-at-a-time previews (`tone-preview.ts`) that stop when the list closes or the app backgrounds. Each tone has its measured `lufs` (morning -17.4, digital -19.6, generic -5.9, dreamcore -18.6) and a `toneVolume` that brings it to about `TONE_TARGET_LUFS` (-17): generic plays at 0.28; the others stay at 1, since a player can't go above full volume. The ringer and the previews both apply it.
- **In the app** (`AlarmHost`, mounted in the root layout): while the app is in the foreground, a once-a-minute check (`alarm-schedule.ts`) rings due alarms through `alarmRinger` (`alarm-ringer.ts`). The tone loops at its `toneVolume`, fading in over 3 s, even in Silent mode. A strong vibration (3 heavy taps) repeats every second, ignoring the weather Vibration setting. It auto-stops after 10 minutes; Snooze is 9 minutes. While snoozed, `alarmRinger.snoozed()` returns the ring to come (its `at` is when); `extendSnooze()` moves it 5 minutes later (and its backup notification), and `dismissSnooze()` cancels it. Each ring (alarm + minute) starts once, whether the minute check or a notification sees it first. A non-repeating alarm keeps its ring time in `onceAt` and switches off when it rings, or on the next launch if its minute passed while the app was closed. Repeating alarms stay on.
- **Ringing screen:** the root-stack route `/alarm-ringing` (`ringing-screen.tsx`, full screen, can't be swiped away), opened by `AlarmHost` whenever something rings, and reopened if anything navigates away mid-ring. It shows the date (and the label, unless it's the default "Alarm"), the giant time, the weather from the `ringWeather` slot ("Wind now, 64°" and "Playing the wind sound"), `SunRings` pulsing with each buzz tap, and 72pt Snooze 9 min and Stop buttons side by side. After Snooze it stays open: "Snoozed", a mm:ss countdown to the next ring, "Rings again at 6:39 AM", the weather, and Add 5 min and Stop (Stop cancels the snooze); it closes once there's neither a ring nor a snooze (in landscape, over bedside mode: the text on the left, the buttons side by side on the right, no rings, inside the same safe area as bedside mode: the larger side inset on both sides plus 16pt), keeps the screen awake, and announces "Alarm, <label>, <time>". The Weather tab treats it as "not on Weather", so the ambient sound fades out under the alarm.
- **Bedside mode:** the switch on the Alarms tab opens `/bedside` (`bedside-screen.tsx`), after `design/frames/9 · Centered dome@2x.png`. `useKeepAwake` keeps the app open, so alarms ring with sound.
  - **Orientation:** landscape only, either way up (so the charger can be on either side); the rest of the app is portrait. app.json allows every orientation (`"orientation": "default"`, with the expo-screen-orientation plugin's `initialOrientation: PORTRAIT_UP` for real builds), and `bedside-orientation.ts` decides: `lockPortrait()` at launch (root layout) and when bedside closes, `enterLandscape()` when it opens. A round 44pt outline Flip screen button (top right) switches between landscape left and right, for when rotation lock is on, and remembers the side in AsyncStorage (`bedside.landscapeSide`). Before the first flip, either landscape side works. On iOS 27 the system can refuse a lock while the app is resizable; failures are ignored.
  - **Safe area and scale** (`bedside-layout.ts`, plain math): everything, the Flip button included, stays inside the safe area plus 16pt (`BEDSIDE_MARGIN`): the larger of the left and right insets on both sides (iOS reports them equal in landscape, so this clears the Dynamic Island on either side and right after a flip), and the top and bottom (home indicator) insets. The layout is one scale factor of the 844x390 reference applied to that area (side columns 144, gap 12, dome 532, clock 108, AM/PM 23, temperature 46, alarm times 22, small text 14): never above 1.0 (a roomier phone or an iPad gets more space around the dome, nothing stretches), never below 0.75, and no text under 12pt. On an iPhone 15 (852x393, 59pt insets) that's 0.83: a 442pt dome, a 90pt clock with 19pt AM/PM, 120pt side columns, 38pt temperature, 18pt alarm times, and 12pt small text. The Flip button stays 44pt. Bedside and the ringing screen are fullScreenModals with their own `SafeAreaProvider`: the app's root one (from Expo Router) measures the screen underneath, which doesn't rotate with the modal, so its insets can stay portrait. Bedside is sized from its own `onLayout` (not the window) and re-renders when the rotation finishes. Safety net (`sideInset`): a landscape window wider than 2:1 that reports 0 on both sides is a notch or island phone, so it uses 59pt (`ISLAND_FALLBACK_INSET`) on both sides. **Expo Go limits.** Everything above runs in Expo Go, with these limits: the notification plays the default iPhone notification sound once, not the alarm tone (custom notification sounds need a native build); nothing rings with sound if the app is closed or the phone locks while bedside mode is off (JavaScript doesn't run in the background, so only the notification fires); the tone plays at the phone's current media volume (an app can't raise the system volume); and expo-notifications logs a "not fully supported in Expo Go" warning at startup, which is about remote push and is expected.

**Ring events.** `alarmRinger.onRingStart(ring)` and `onRingEnd(ring, reason)` (`reason`: `'stop'`, `'snooze'`, or `'timeout'`) let code outside `src/features/alarms/` follow rings, and `setToneGain(gain)` (0-1) turns the ringing tone down or back up over about a second (tone volume = `toneVolume` × fade-in × gain). The gain resets to 1 when the ring ends. Alarm code only fires the events and exposes the gain; it doesn't know who listens.

**Weather on wake** (`src/services/wake-weather.ts`, registered once from the root layout). Sound only, no UI or setting:
- **Ring start:** reads the current conditions right away: Developer test weather, or the last saved live forecast (its hourly forecast for this hour if it's over an hour old). Demo filler doesn't count, so with no weather the alarm rings normally at full tone. It stops any cue preview and alert beeps, then plays the conditions' loops through `ambientSound.setWake` (wake mode). Wake mode plays on any tab, in Silent mode, and with "Ambient sound" off, at `WAKE_VOLUME` (1.0, with the usual layer balancing), fading in over 4 s, 0.5 s after the tone starts. VoiceOver's lower volume and alert ducking don't apply, and a user preview still takes over. A severe alert's conditions play, without its beeps. No condition vibrations or light cues play, so the alarm's buzz is the only vibration.
- **Balance:** the weather's level is its loudest layer (`lufs` + its layer volume in dB, via `layerVolumes`), and the tone's level is its `lufs` + `toneVolume` in dB. If the tone is more than `WAKE_MAX_GAP_LU` (10) louder, `setToneGain` lowers it until the gap is exactly 10 LU, but never below `WAKE_MIN_TONE_GAIN` (0.35), so the alarm can still wake someone. Within 10 LU, the tone stays at full. Both constants are at the top of `wake-weather.ts`, to tune by ear. With today's files nothing reaches the floor: thunderstorm leaves every tone at full, clear takes Classic to 0.96, and light rain takes the tones to 0.47-0.64.
- **Ring end:** after Snooze or the 10-minute timeout, the weather fades out with the tone (1 s). After Stop, it keeps playing for 10 s, then moves over 3 s to whatever the Weather tab wants: silence on another tab, or its normal loop at the normal level on Weather. A new ring during those 10 s takes over.

`alarmRinger.stop()` still has its "NEXT PHASE" comment for what comes after waking (fading the weather in after Stop so you hear it before you look).

**Future work: AlarmKit (iOS 26).** Apple's AlarmKit lets an app schedule real system alarms that ring with its own sound through Silent mode and Focus, show on the Lock Screen and Dynamic Island, and work when the app is closed. It needs a native module and a development build (not Expo Go), so it replaces the notification backup later.

## Preferences

The Preferences tab holds every setting, in this order: Name, Appearance (the app's System/Light/Dark, then the Bedside mode row: Auto, System, Light, Dark, each on one line, subtitle "Auto follows sunrise and sunset. System follows your iPhone."), Opening screen, Temperature, Sound and vibration, Accessibility, Developer. `src/app/(tabs)/preferences.tsx` composes them: `PreferencesPage`, `NameSection`, and `OpeningScreenSection` come from `src/features/preferences/preferences-screen.tsx`; the weather-dependent sections come from `src/components/app-settings.tsx` and `src/components/developer-settings.tsx`. Rows (`src/components/settings-rows.tsx`, theme-only so the feature can use them) follow `design/frames/12_Preferences.png`: bare rows between thin lines, bold title with a subtitle, and a drawn toggle (`switch*` tokens).

The opening screen setting picks which tab the app opens to: Weather from the morning time (AM, default 9:00 AM) until the evening time (PM, default 7:00 PM), Alarms otherwise. The rule is the pure `getStartTab(now, morning, evening)` in `src/features/preferences/opening-time.ts`. `src/app/index.tsx` redirects to the right tab on cold launch (before any tab mounts, so a night launch never starts the weather sound), and `useStartTabOnReturn` in the tab layout does the same after 5+ minutes in the background. Saved in AsyncStorage under `openingPreferences`. Its name field (optional, up to 15 characters, saved in the same store) personalizes the Weather greeting ("Good morning, Jolie!"). Preferences › Developer › "Simulate time" overrides the time for this logic and the Weather screen greeting (`getGreeting` in `src/services/greeting.ts`), while Developer mode is on. `src/features/preferences/` must not import weather or alarm code.
